How to review

  1. Read the three approach summaries below (2 minutes). Each one is built around a different main idea: monitoring, conversation, and visual progress.
  2. Open each desktop file and scroll through its 14 views. The same sample data appears everywhere: six projects, seven AI personas, and you as owner. That way you're comparing layout and interaction, not content. Each view has a short "Look for" note and the requirement IDs it covers.
  3. Open each mobile file (9 screens). Imagine using it one-handed, on a trail or in a queue. FR-35 puts answering questions, reviewing work, checking status and approving gates first on mobile.
  4. Run the same three tasks in every approach and note which felt fastest and clearest:
    ① Find out which projects need you and why. ② Answer Forge's blocking question about OpenCode. ③ Decide whether the T-142 handoff is good enough to continue.
  5. Pick, don't just rank. Choosing one approach outright is fine, but mixing is expected (FR-122). For example: "A's catalog and settings, B's desk and handoff letter, C's roadmap timeline." Use the feedback template.
  6. Flag requirement changes. Some mockups stretch the requirements on purpose (see gaps found). If a mockup changes your mind about a requirement, say so.

What these mockups are not: they aren't final visual design, copy or data. Colors, fonts and density are there to make each approach's character obvious. A chosen direction would be restyled against the global frontend standard. All links between views are illustrative; only the reviewer bar at the top of each page navigates.

The three approaches

Approach A

Mission Control

An operations console: a persistent sidebar, dense tables and panels, and tabs inside each project. Everything is one click away and shown at once.

  • Strong at: scanning many projects and sessions; power-user speed; a familiar pattern (like GitHub or Linear)
  • Weak at: feeling like "a team"; first-run clarity; explaining why
Desktop →Mobile →
Approach B

Team Room

Conversation first. Each project is a room where personas post updates, ask questions and present work. A "Desk" lets you work through what's waiting one item at a time. Warm, editorial typography.

  • Strong at: "interactive, like working with a team"; quick replies; context and reasoning; handoffs as letters
  • Weak at: status can get buried in chat; less dense; harder to compare many projects
Desktop →Mobile →
Approach C

Roadmap Canvas

Show the work as a picture: a lifecycle board, roadmap timelines with gates, relay lanes for sessions, a decision tree for option sets, and matrices for the team and standards. Icon rail plus ⌘K palette. Dark theme.

  • Strong at: seeing progress, dependencies and decision history; showing CLI parity in the palette; distinctive
  • Weak at: most effort to build and test; can be visually noisy; dark-only feel
Desktop →Mobile →

Questions for you

Across all three

  • Which landing page answers "what needs me and where does everything stand?" fastest?
  • Is the triage list (A), one-at-a-time desk (B) or urgency board (C) the right model for questions?
  • Which handoff presentation would make you trust a handoff without reading the transcript?
  • Light, warm or dark? Should the app offer a theme toggle regardless?
  • How important is the ⌘K command palette that shows the CLI command for each action (C, view 14)? It could be added to any approach.

Approach-specific

  • A: Is the density right, or too much on a laptop screen?
  • B: Do status sentences ("Forge is handing off…") help, or would you rather see numbers?
  • B: Should rooms be real chat where you can talk to personas any time, or only structured messages?
  • C: Is grouping the catalog by lifecycle stage better than sorting by "needs you"?
  • C: Is the trace map (requirements ↔ values ↔ decisions) worth building early?

Requirement gaps found while mocking

Drawing every view turned up places where the requirements are silent or ambiguous. These are worth deciding regardless of which approach you choose:

FindingRelatedSuggested action
Unified "needs you" stream. Every approach ended up combining questions, gates, reviews and option sets into one place. The requirements only define a questions dashboard.FR-104Widen FR-104 to "everything awaiting a human decision".
Rev 2: smart handoffs are now experimental (§8.2), so this can wait until they graduate. Handoff approval. Each mockup lets a human (or Lens) check a handoff before the next session starts. The requirements don't say whether handoffs are automatic or gated.FR-72–74Add a setting: auto-continue, reviewer-persona check, or human approval.
Rev 2: deferred with handoffs. Handoff templates. Mockups show role-specific templates (e.g. developer-v3) and let you compare a session's handoff with the one before it.FR-73Add a requirement for versioned handoff templates per role.
Context usage confidence. OpenCode and Antigravity usage may be estimated. The UI needs to show measured vs. estimated.FR-71, Q2Require the adapter to report whether usage is measured or estimated.
Human vs. persona reviewer. Lens (AI) and you both review. The order and authority aren't defined.FR-54, FR-110Define it: Lens checks first, then a human approves (as mocked), with a per-project option.
Notifications on mobile. Email is out of scope, but without some notification a blocking question can wait for hours.FR-106Consider PWA web push as the minimum. It isn't email.
Answered-question cost. Mockups show "blocks 2 tasks · waiting 12m" and, in C, roadmap slip.FR-102Add "show the impact of leaving a question unanswered".
Theme. No requirement covers light/dark.FR-34–35Add light + dark themes following the system setting.
Multi-user (Q4). Tailnet identity appears in headers and history. Rev 2: rehearsals now show a second human reviewer (maria, FR-117a), so Q4 matters sooner.FR-17, Q4Decide Q4 before building review assignment.
