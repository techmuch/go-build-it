Summary

The app is good at the delivery half of the vision and at keeping people in charge. It is weaker where the vision is most distinctive: evidence at the moment of approval, one place for a person's attention, and showing the loop from discovery to release.

The four that matter most

  1. F-01Approval is possible without evidence. A review can be approved with every evidence tile empty, the phone shows a green "pass" when no test ran, the 16 standards are never assessed, and a release can be made while a gate is pending.
  2. F-02The desktop has no single "needs you" list. What is waiting for you is spread over five sidebar entries with five badges (Questions 3, Sessions 1, Reviews 1, Options 1, Rehearsals 1), and proposed values are a sixth kind found only inside Artifacts.
  3. F-03The app is organised by kind of thing, not by the loop. No screen shows where a project is in the loop from discovery to release, or what it is waiting for.
  4. F-04Every decision has one decider. Questions, option sets, rehearsals and reviews each record one person's choice.

What already works well

  • People decide, agents do. Questions state why they matter and what the member recommends. Any member's terminal can be watched, taken over and handed back.
  • Gates on small slices. A milestone has a gate with criteria, and tasks behind it say they are waiting for it.
  • Real evidence exists. Traceability names its gaps, compare remembers which screenshot was accepted, and the doctor shows the proof for every check.
  • The phone. One Inbox, one thumb, the right order.

How to read this: the screenshots come from a seeded demo whose AI members are scripted, so empty test results and "Fake Lens" text are demo data. Findings are about what the screen allows and shows, which is the same with real members.

Workflow

The vision's loop, and where a person meets a break when following it through the app today.

1 · Discover

Requirements, mockups, values and option sets exist and link to each other. Break: they live under Artifacts and Options with no shared view of "what is still undecided". No interview or conflict record.

2 · Gate

The dress rehearsal and compare are the gate. Break: the thing being judged is too small to see, and approval records one person. There is no baseline to approve.

3 · Deliver

Queue, sessions and terminals work, and blocked members reach you. Break: the same blocked member appears as a session, a question and an inbox item, with different statuses.

4 · Release

Courier releases without an AI session. Break: review and release accept approval with no evidence, and nothing assembles the record of a release.

The return path, "working software to react to, early and often", is the rehearsal and compare screens. Feedback from a rehearsal does follow the task into its review, which is the loop closing once.

Findings

Each finding, the idea it touches, and a proposed change. Screens link here by number.

F-01 Approval is possible without evidence High 06 Evidence, not assurance

A review can be approved with every evidence tile empty, the phone shows a green "pass" when no test ran, the 16 standards are never assessed, and a release can be made while a gate is pending. The vision says each release carries the tests that ran, the screens against their mockups, and who approved what; no screen assembles that.

Proposed: Make the verdict depend on the evidence: no default verdict; Approve asks for a reason when tests did not run, a mockup is not matched or a requirement is unassessed; show "not run" in grey, never "pass". Assess only the standards that apply, with the reviewer member's finding beside each. Add a release record page listing tests, compare results, requirements covered and approvals.

Seen on: S19 S23 S27 S41

F-02 The desktop has no single "needs you" list High 01 Agreement is the scarce thing

What is waiting for you is spread over five sidebar entries with five badges (Questions 3, Sessions 1, Reviews 1, Options 1, Rehearsals 1), and proposed values are a sixth kind found only inside Artifacts. The vision treats a person's attention as the scarce thing. The phone already has one Inbox with all eight items in the right order.

Proposed: Give the desktop the phone's Inbox as its first sidebar entry, with one count. Keep Questions, Reviews, Options and Rehearsals as filters of it.

Seen on: S04 S16

F-03 The app is organised by kind of thing, not by the loop High 05 Small true slices

No screen shows where a project is in the loop from discovery to release, or what it is waiting for. The sidebar lists objects (questions, sessions, queue, reviews, options, rehearsals), the stage is a dropdown set by hand, and there is no baseline: nothing records which requirements and mockups a slice was approved against.

Proposed: Put a loop strip at the top of the project overview (Discover → Gate → Deliver → Release) showing counts and the one thing that is holding the project. Derive the stage from it. Add a baseline: a named, approved revision of requirements and mockups that a milestone is built against.

Seen on: S01 S02 S06 S15 S31 S33

F-04 Every decision has one decider High 03 Conflict is information

Questions, option sets, rehearsals and reviews each record one person's choice. The vision's stakeholders with different aims, and the record of where they conflict and how it was settled, have no screen. This is known to be unbuilt; the review notes where it would attach.

Proposed: Covered by requirements rev 12 and the user management mockups. When that is built: ask a named person or group on a question; show each stakeholder's pick on an option set; record each reviewer's sign-off at a gate; add a conflicts list beside Values.

Seen on: S05 S11 S12 S20

F-05 Mockups and screens are hard to see where they are judged Medium 06 Evidence, not assurance

Compare squeezes the mockup into a thin strip and stacks "side by side" vertically. The rehearsal shows the screen at a third of its size on the desktop and as an empty box on the phone. Option previews are cut off. These are the three screens where a person approves what they see.

Proposed: Scale each preview to fit its frame at the mockup's own width, put the two panes next to each other from 1100 pixels up, and load the real preview on the phone rehearsal.

Seen on: S07 S11 S12 S13 S42 S43 S48

F-06 Status says different things in different places Medium 06 Evidence, not assurance

A task is "running" in the queue while its session is "blocked · needs you". herdr setup says "all good" beside "✖ static 13/14". Remote access checks are worded as passes beside warning icons. A blocked session explains itself at the bottom of the page.

Proposed: One status per thing, computed once: a task whose session is blocked shows "waiting for you" with a link. Word each check as what was found. Put the reason a session is blocked at the top, with the action.

Seen on: S03 S14 S15 S17 S10b S29 S30 S45

F-07 The history is complete but hard to read Medium 06 Evidence, not assurance

Document actions appear twice (the action and its commit), routine updates have no reason, adding a team is seven rows, and "Related to" shows unrelated events. The record is there; the decisions in it are hard to find.

Proposed: Fold a commit into the action that caused it, group runs of the same kind, add a "Decisions" filter (answers, choices, approvals, values), and give the project history the same search as the global one.

Seen on: S24 S25 S26

F-08 Traceability is strong and hidden Medium 02 Discovery never finishes

The traceability table is the best evidence in the app, and it is a toggle inside one tab. Its gaps do not reach the overview or "Needs you". Changing a requirement does not yet mark the mockups, tasks and screens that rest on it.

Proposed: Show gap and drift counts on the project overview and catalog card. In the editor, list what a requirement touches before saving, and mark those items "check again" after.

Seen on: S02 S06 S08 S09

F-09 Machine detail leaks into decision screens Low 01 Agreement is the scarce thing

Temporary folder paths in the Settings title, the Repository card and the member card (where it overflows); the launch command with environment variables at the top of every terminal.

Proposed: Shorten paths to the last two parts with the full path on hover; start the terminal view after the launch line.

Seen on: S02 S17 S18 S21 S29 S45

F-10 Small defects Low

"◀ Step 0" on the first rehearsal step. An unknown milestone address shows an empty page. The editor without a file says only "No document path given". ⌘K for "review" lists help pages before the open review. Atlas coaches Atlas. The phone document view is soft and its tabs are cut off. The project tabs vanish in the editor.

Proposed: Fix each; none needs a design decision.

Seen on: S03 S09 S12 S20 S36 S47

F-11 Artifacts tabs are flexible in the file but fixed in the UI Medium 02 Discovery never finishes

A project can have any tabs through docs/gbi.toml or the CLI, but the UI only offers the four standard names, labels are a fixed list of nine, Compare needs a tab named "mockups", and the phone lists the standard tabs.

Proposed: Add "New tab…" to "Set as entry point", allow project labels, show Compare whenever files are labelled mockup, and read the tab list on the phone.

Seen on: S06 S10 S10b S38

F-12 Empty states and repeated text Low 01 Agreement is the scarce thing

"No stable release yet" three times per card, columns that are empty for every row, a page of zeros on History, twenty-six help pages on the phone's More.

Proposed: Hide what is empty, say it once, and give each empty state the next step.
