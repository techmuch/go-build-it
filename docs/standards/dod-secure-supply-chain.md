# DoD secure build and supply chain

How the software is built, scanned, packaged and delivered so that an assessor can trust what is running. It covers FIPS cryptography, the software bill of materials (SBOM), static analysis, vulnerability scanning, containers and the pipeline. Part of the DoD set: see *DoD ATO readiness* for how rules, overrides and evidence work.

- Every rule has an ID (`SSC-21`). **SHALL** rules block a merge.

## FIPS 140-3 cryptography

- **SSC-01** SHALL: Release binaries are built with Go's native **Go Cryptographic Module**, selected at build time with `GOFIPS140` set to a version that holds a CMVP validation certificate (for example `GOFIPS140=v1.0.0`, certificate #5247). This turns FIPS 140-3 mode on by default and keeps the build pure Go (`CGO_ENABLED=0`).
- **SSC-02** SHALL: The module version is pinned by number, not by the `certified` or `latest` alias, so a toolchain upgrade cannot change the validated module without a reviewed change. `GOFIPS140=latest` and `inprocess` are not used for a release: they select modules that are not validated.
- **SSC-03** SHALL: `GOEXPERIMENT=boringcrypto` and OpenSSL through cgo are not used. They are unsupported or need cgo, and they cannot be combined with the native module.
- **SSC-04** SHALL: The system profile records the module version, its CMVP certificate number, the certificate's sunset date and the operating environment it runs in. The operating system and processor are checked against the certificate's tested environments, and a difference is raised with the ISSM.
- **SSC-05** SHALL: The test suite also runs with `GODEBUG=fips140=only`, which makes any non-approved algorithm fail. That setting is for tests only and is never used in production.
- **SSC-06** SHALL: The pipeline confirms the built binary reports FIPS mode (`go version -m` shows the `GOFIPS140` setting) and attaches the output to the release evidence.

## Dependencies

- **SSC-10** SHALL: Dependencies are pinned in `go.mod` and `go.sum`, and in `package-lock.json` for the frontend. Builds use `-mod=readonly` and `npm ci`, and fetch modules only from the approved proxy or a vendored copy. The build works with no internet access.
- **SSC-11** SHALL: A new dependency is approved in an ADR that records its purpose, licence, maintainer, release history and known vulnerabilities. Software that is no longer maintained, or has no security support, is not used (SA-22).
- **SSC-12** SHALL: Every release has an SBOM in CycloneDX or SPDX format, generated by the pipeline from the built artifact (with `syft` or `cyclonedx-gomod`), covering Go modules, frontend packages and the container image. It lists every component, direct and nested, with its version and hash.
- **SSC-13** SHALL: The SBOM is regenerated for every build that changes a component, stored with the release, and signed with it.
- **SSC-14** SHALL: Build information is left in the binary (`go version -m` works), so scanners can read its modules. `-trimpath` and `-ldflags "-s -w"` are used to remove local paths and debug symbols.

## Scanning

- **SSC-20** SHALL: Every pull request and every build of the main branch runs these, and a failure blocks the merge (SA-11, RA-5):
  - `go vet` and `staticcheck`
  - `gosec`, for Go security defects
  - `govulncheck`, which fails on any known vulnerability the code can reach
  - `npm audit --omit=dev` for the frontend
  - a secrets scanner (for example `gitleaks`) over the change and the history
  - a scan of the container image for vulnerabilities and STIG compliance
- **SSC-21** SHALL: A finding is fixed, or recorded in the POA&M with a mitigation and a due date. The defaults are 30 days for critical and high, 90 for moderate and 180 for low, unless the AO sets shorter times.
- **SSC-22** SHALL: A scanner finding is silenced only on the line concerned, with a comment that gives the reason and the POA&M or ADR reference. Rules are never switched off for the whole project.
- **SSC-23** SHALL: Vulnerability scans run again every day against the released artifact and its SBOM, because new vulnerabilities are found in old code. A new finding opens a task.
- **SSC-24** SHALL: The running application is tested with a dynamic scanner (DAST) against a deployed test instance before each release, with an authenticated user of each role.
- **SSC-25** SHALL: Scan reports are kept with the release as evidence, in the machine-readable format the AO's tools accept.

## Containers

- **SSC-30** SHALL: When delivered as a container, the image is built from an approved hardened base (a DoD Iron Bank image, or the base the platform names), pinned by digest. A minimal or distroless base is used, with no shell and no package manager.
- **SSC-31** SHALL: The final image contains the binary, its certificates and its static files, and nothing else. The build uses a multi-stage file, and no compiler, test tool or source reaches the final stage.
- **SSC-32** SHALL: The container runs as a numbered non-root user, with a read-only root file system, no added capabilities and no privilege escalation.
- **SSC-33** SHALL: No secret, key, token or certificate private key is in any image layer or build argument.
- **SSC-34** SHALL: The image exposes only the ports in `docs/ato/ports-protocols.md`.

## Pipeline and provenance

- **SSC-40** SHALL: Release artifacts are built only by the pipeline, from a tagged commit on the protected main branch. Nothing built on a developer's or an AI member's machine is released.
- **SSC-41** SHALL: The software does not download or install its own updates. A new version reaches an environment only through the authorized pipeline and the platform's change process (CM-3).
- **SSC-42** SHALL: The pipeline signs every artifact, image and SBOM, and records provenance: the commit, the builder, the toolchain version and the inputs. The deployment verifies the signature and refuses anything unsigned.
- **SSC-43** SHALL: The same commit, toolchain and inputs produce the same binary. A second build is compared in the pipeline, and a difference fails it.
- **SSC-44** SHALL: The Go toolchain and Node versions are pinned by exact version and verified by checksum. The pipeline's own actions and images are pinned by digest or commit, not by a moving tag.
- **SSC-45** SHALL: The main branch is protected: no direct pushes, signed commits, review by a person who did not write the change (ATO-53), and passing checks before merge.
- **SSC-46** SHALL: Pipeline credentials are short-lived and scoped to one job. AI members cannot read them and cannot change the pipeline definition without a person's review.
- **SSC-47** SHALL: The same artifact is promoted from test to production. It is not rebuilt between environments.

## Before asking for review

All of these pass in the pipeline:

```
GOFIPS140=v1.0.0 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" ./cmd/...
go version -m <binary>                      # shows GOFIPS140; saved as evidence
GODEBUG=fips140=only go test ./...          # tests only
go vet ./... && staticcheck ./... && gosec ./...
govulncheck ./...
npm ci && npm audit --omit=dev
gitleaks detect
syft <artifact> -o cyclonedx-json > sbom.json
```

## Why

- **Validated cryptography is a hard gate.** Only a module with a CMVP certificate counts. Go's native module has one, needs no cgo and keeps the single static binary, so it is the simplest way to comply.
- **You answer for your dependencies.** An SBOM made from the built artifact, with daily scans against it, is how a team learns that yesterday's safe release is vulnerable today.
- **Trust the pipeline, not the person.** Signed, reproducible builds from a protected branch let an assessor confirm that what runs is what was reviewed, whoever or whatever wrote it.
